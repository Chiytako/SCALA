# RecGen 調査報告

**2026-07-28 〜 07-29 / SCALA / 実行環境: GB10（費用ゼロ）**

RecGen が HierGen を再現しない問題の調査。第3ラウンドで**基準そのものが壊れて
いた**ことが判明し、第1〜2ラウンドの結論の一部を撤回する。

英語の技術記録は [`findings.md`](findings.md) §4b〜4i にある。この文書はその調査
過程を日本語で通しで残したもの。

> **この文書の §1〜§4 は当時の記録であり、結論は §5 以降で訂正されている。**
> 経過を残すのは、間違った測り方が5アームの順位をまるごと反転させた事例だから。
>
> **結論だけ必要なら §8d へ。** RecGen は動く ── ただし論文の代入規則ではなく、
> 中間エンコーダのキャッシュに上限を設けることによって。既存チェックポイントで
> 再学習なしに KL が 13〜62 分の1になる。

---

## 1. 問題

RecGen は PHOTON の目玉となる効率化手法である。上位レベルの KV キャッシュだけを
保持し、下位のデコーダ縦続には自身の再構成 `X_hat` を食わせることで、KV を大幅に
削減する。論文の Theorem A.6 は `X_hat^(L-1) = X^(L-1)` のとき RecGen が厳密だと
述べる。

しかし本実装では、**4つのモデルサイズすべてで RecGen の出力が HierGen と一致
しなかった**。効率化は本物（KV 12.5分の1、速度 1.5倍）だが、出力が保存されない。

`loss_rec` は毎回 0.90〜1.02 で頭打ちになった。

---

## 2. 診断 — 同じ数字の別の読み方

「両レベルとも cos 0.5」と「片方 0.9、もう片方 0.1」は同じ合計を与える。測定で
分離した（`scripts/recgen_diag.py`）。学習済み 8B での実測:

| level | A: cos(X_hat_j, X_j) | B: cos(post_j, X_j) | RecGen は代入するか |
|---|---:|---:|---|
| L1 | **0.2226** | 0.3955 | **しない** — 本物の埋め込みを使う |
| L2 | 0.6567 | **0.8436** | する |

### 2.1 損失の 69% が、起きない代入を採点していた

`_rec_loss` は `l = 1..n_levels` を回していたが、`_emit_group` が代入を行うのは
`l >= 2` のときだけである。l=1 項は「LM ヘッドへの入力が次トークンの埋め込みと
cos 類似であれ」を要求しており、確率的な言語モデルには原理的に達成できない。

論文の Theorem A.6 自身が「必要なのはボトルネック（L→L−1）の一致だけ」と述べて
いるので、この項は理論上も不要である。

### 2.2 RecGen の代入は生成内容に一切依存しない

`X_hat_j` はスロット j を*予測した*デコーダ状態であり、**スロットが生成される前**
に計算される。つまり上位デコーダは、下位で実際に何が生成されたかの情報をゼロしか
受け取らない。

---

## 3. 対策（第1案） — ChunkGen

chunker は線形1つでキャッシュ不要なので、実際に生成されたユニットに適用しても
コストはほぼゼロである。

    hiergen   unit_j = encoder(chunker(生成物))   厳密、キャッシュが要る
    recgen    unit_j = X_hat_j                    生成物に依存しない
    chunkgen  unit_j = chunker(生成物)            キャッシュ不要、かつ依存する

`scala/infer/generate.py` に第3の `Mode` として実装した。

## 4. A/B — 5アーム

GB10 上で同一アーキテクチャ（v4）・同一データ・同一シード・同一 610 ステップ
（80M トークン）。目的関数だけを変えた。**この時点では「HierGen との一致率」で
順位づけし、`nolrec`（`L_rec` を捨てた構成）が最良と結論した。**

その結論は §6 で覆る。

## 5. 第3ラウンド — 基準が壊れていた

### 5.1 HierGen は学習時 forward と一致していなかった

`scripts/protocol_diag.py` を書き、各プロトコルを **HierGen ではなく教師強制の
学習時 forward** に対して採点した。HierGen はその forward と厳密一致するはずで、
`test_hiergen_matches_the_training_forward` がそれを保証している。

学習済み `nolrec` での実測は **一致率 61.0%、KL 0.247**、ロジットの最大差 7.65。
float32 でも同じ、未学習モデルでは 100% / 7e-6。つまり**丸め誤差でも実装の
段取りの問題でもなく、学習済みの重みでのみ現れる**。

原因は `Attention.forward_mla_absorbed` ── 重み吸収 MLA の経路が
**attention 出力ゲートを適用していなかった**こと。この経路は `LatentKVCache`
経由でしか通らない、つまり**生成時専用**である。学習は非キャッシュ経路を使い、
そちらはゲートを適用する。

結果として、`qk_norm: false` かつ `output_gate: true` の MLA を持つ全チェック
ポイント ── 8B の2本と 250M v4 の全アーム ── が、**学習したのとは別の関数で
生成していた**。

### 5.2 なぜ32件のテストを素通りしたか

独立に2つの理由があり、どちらも `findings.md` §6（初期化バグは静かに通る）の実例
である。

* **`w_gate` の初期値は 0** で、ゲートは `2*sigmoid` なので新品のモデルでは
  ちょうど 1.0 になる。1.0 の掛け忘れは観測できない。そして等価性テストは
  すべて新品のモデルで走っていた。
* **テストが読む唯一の設定 `configs/base_tiny.yaml` は、最上位エンコーダの
  `qk_norm` を true にし、`output_gate` を書いていない。** QK-Norm は重み吸収を
  無効化するので、**テストしていた経路は出荷される経路ではなく**、落ちていた
  モジュールはそもそも生成すらされていなかった。

新しいテストは `qk_norm=False, output_gate=True` を強制し、
`_shake_zero_init_parameters` で **`__init__` が 0 にする全パラメータに実値を
入れる**。修正を stash して両方が落ちることを確認済み（通ることだけ確認しても
意味がない）。

**得られた規則**: 2つの経路が同じ関数だと主張するテストは、**初期化器が生成
しない値の上でしか有効ではない**。ゼロ初期化は中立な入力ではなく、モジュールを
まるごと観測不能にする唯一の設定である。

修正後、同じチェックポイントで HierGen は **97.6% / KL 0.0017** ── bf16 の
ノイズ下限であり、この指標が本来示すべき値になった。

なおこのバグは**推論専用**なので、§4 の token CE はすべて有効である。動くのは
一致率と KL の列だけで、それらは 39% ずれた HierGen と比べられていた。

## 6. 訂正 — 5アームの順位は反転する

基準を直しただけで、再学習はしていない:

| arm | α | chunk_p | token CE | hiergen | content_only | up_only | **ChunkGen** | RecGen |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| ctl | 0.30 | 0.00 | 4.4649 | 98.4% | 72.4% | 66.9% | 43.4% | 32.0% |
| lossonly | 0.30 | 0.00 | 4.4954 | 98.5% | 74.0% | 76.1% | 60.9% | 29.1% |
| **fix** | 0.30 | 0.25 | **4.4641** | 98.7% | 88.3% | 81.3% | **71.1%** | 31.0% |
| chunk10 | 0.30 | 1.00 | 4.5486 | 98.4% | 66.2% | 77.6% | 53.4% | **53.9%** |
| nolrec | 0.00 | 1.00 | 4.4825 | 97.6% | 79.2% | 64.6% | 56.2% | 36.3% |

**§4 の結論は誤りだった。** 当時は `nolrec` 52.3% > `fix` 49.4% と読み、
「最良の構成は再帰的整合性損失を完全に削除する」と書いた。正しい基準では
**`fix` が 71.1%、`nolrec` が 56.2%** で15ポイント差がつき、しかも `fix` は
`L_rec` を α=0.30 で**残している**アームである。token CE も5アーム中で最良。

したがって旧 §6 の推奨設定（`rec_loss_alpha: 0.0`, `chunk_cond_prob: 1.0`）は
**撤回する**。

2つのレバーが干渉するという観察自体は正しかったが、符号を読み違えていた。解は
どちらかを捨てることではなく**両方を中庸にする**こと（α=0.30, chunk_p=0.25）
である。chunk_p=1.0 は `L_rec` の有無にかかわらず一致率を落とす（53.4% / 56.2%）。

**プロトコルを別のプロトコルで採点したことが、5アームの順位をまるごと反転させた。**
学習時 forward で採点すること ── 系の中で唯一、検証対象のコードを参照せずに
定義できる量だからである。

## 7. 誤差は「誰も学習していなかった側」にあった

正しい基準が手に入ると、2つの代入を分離できる。完成した level-(l-1) ユニット群は
**2か所**で消費され、それらは独立である。

    content   level-l デコーダがスロット j の content として読むもの。
              `chunk_cond_prob` が学習しているのはこちら。
    up        level-l chunker への入力、ひいては level-l エンコーダへの入力。
              ここで代入すると **X^(L) 自体が壊れる**。そして
              `encode_all` は `chunk_cond_prob` の値にかかわらず常に本物の
              エンコーダを通すので、**この代入を学習している項は存在しない**。

`recgen` と `chunkgen` は両方を同時に代入する。だから4ラウンドかけても2つの誤差を
区別できなかった。下位キャッシュを保持したまま片方ずつ代入する診断用の2つを
足すと、`nolrec` で:

| プロトコル | content | up | 学習時 forward との一致 | KL | cos(X_top) |
|---|---|---|---:|---:|---:|
| hiergen | encoder | encoder | 97.6% | 0.002 | 1.0000 |
| content_only | chunker | encoder | 79.2% | 0.193 | 1.0000 |
| up_only | encoder | chunker | 64.6% | 0.598 | 0.7296 |
| chunkgen | chunker | chunker | 56.2% | 0.875 | 0.7295 |
| recgen | xhat | xhat | 36.3% | 1.702 | 0.3557 |

**`up` 側が 36.1pt、`content` 側が 20.9pt。** 4ラウンドは小さい方を調整して
いた。そして大きい方は、`encode_all` の計算内容を変えない限りどんな目的関数でも
届かない。

`cos(X_top)` がより直接に語る。上向きの代入は最上位の条件付け状態を真値に対して
cos 0.73 まで（最終グループでは 0.69、まだ漂流中）、RecGen では 0.36 まで崩す。
その状態は系列全体の文脈を運ぶ唯一の経路である。

## 8. 対策（第2案） — 厳密な方を安くする

RecGen が存在する理由は「中間エンコーダの KV キャッシュが系列長に比例して
伸びる」ことである。その代償が「`X_hat_j` はスロット j が生成される前に計算
される」ことで、**この代償は学習では払えない**。`X_j` に一致させるとは、まだ
サンプリングしていないトークンの要約を予測せよということだからである。エントロピー
が 0 でないモデルには不可能である。

これが Theorem A.6 の正直な読み方である。前提（再帰的整合性）は**未達成なのでは
なく到達不能**である。論文自身も検証していないと明記している ──
"we leave a more rigorous likelihood-based evaluation of RecGen for future work"
── し、一致率の数値は一切報告していない。

ならばキャッシュの増大の方を直接叩けばよい。**level-l エンコーダ（l < L）を、
level-(l+1) ユニット1つを構成する `C_{l+1}` 個のユニットに閉じ込める** ──
メタグループ境界を越えないブロック因果 attention にする。すると:

* グループ外は決して読めないので、キャッシュは1グループ分で境界ごとに書き潰される
  ── **系列長に対して O(1)**。これは RecGen が買っていた節約そのものである
* 上と横に渡される要約は依然として**本物のエンコーダ状態**なので、
  **HierGen は学習時 forward とビット一致のまま**
* `L_rec` も `chunk_cond_prob` も不要になる。補正すべき代入が残っていない

大域文脈は失われない ── そこには元々無い。最上位エンコーダ（full attention、
`C_<=L` トークンに1回しか走らない）が運び、converter 経由で下位デコーダに届く。

`configs/base_small_blocal.yaml` は `nolrec` と `encoder_block_local: true`
および目的関数の2つのつまみを 0 にした点だけが違う:

| | nolrec | blocal |
|---|---:|---:|
| パラメータ | 0.252B | 0.252B（同一） |
| KV/token, HierGen | 0.945 KiB | **0.207 KiB** |
| KV/token, RecGen | 0.195 KiB | 0.195 KiB |

**厳密な生成が、近似生成の 6% 増しで済む**（従来は 4.8 倍）。

### 8.1 A/B 結果（GB10、他5アームと同一条件）

CE は末尾100ステップ平均、6アームすべて同じ方法で再計算:

| arm | α | chunk_p | token CE | **HierGen** | ChunkGen | RecGen | KV/token |
|---|---:|---:|---:|---:|---:|---:|---:|
| ctl | 0.30 | 0.00 | **4.4910** | 98.4% | 43.4% | 32.0% | 0.945 KiB |
| fix | 0.30 | 0.25 | 4.5100 | 98.7% | 71.1% | 31.0% | 0.945 KiB |
| **blocal** | 0.00 | 0.00 | 4.5164 | **98.3%** | 40.8% | 42.7% | **0.207 KiB** |
| lossonly | 0.30 | 0.00 | 4.5182 | 98.5% | 60.9% | 29.1% | 0.945 KiB |
| nolrec | 0.00 | 1.00 | 4.5278 | 97.6% | 56.2% | 36.3% | 0.945 KiB |
| chunk10 | 0.30 | 1.00 | 4.5726 | 98.4% | 53.4% | 53.9% | 0.945 KiB |

**比較すべきは「0.207 KiB で 98.3%」対「0.195 KiB で 71.1%」である。** メモリ 6% 増で、
「10トークンに3つ食い違う」が「bf16 のノイズを除いて完全一致」になる。目的関数を
4ラウンド調整して ChunkGen は 43.4% → 71.1% まで来たが、**エンコーダに何を見せるかを
変える方が残り全部を一度に閉じた**。

`blocal` の ChunkGen / RecGen 列が悪いのは当然で、両方のつまみを 0 にして学習したため
代入に備えていない。読むべき列ではない。

**正直なコスト。** `blocal` は token CE で6アーム中3位、最良の `ctl` に 0.025 nats 負ける。
6アームは1シードで 0.082 nats に散らばっているので「悪い」とは言えないが、「ただ」とも
言えない。level-1 エンコーダを 16 トークンに閉じ込めるのは実際に制約であり、主張は
「安い」であって「無料」ではない。

## 8b. 8B には**別の原因**がもう1つあった

出力ゲートを直した後の公開 8B:

| プロトコル | 学習時 forward との一致 | KL |
|---|---:|---:|
| hiergen | **42.6%** | 0.473 |
| chunkgen | 19.9% | 1.470 |
| recgen | 13.4% | 2.382 |

float32 でも 42.4% なので精度の問題ではない。同じ手順で切り分けると、**4つのスタック
すべて**がバッチ経路と逐次経路で食い違う ── 8 位置しかないデコーダを含めて。ルータを
dense FFN に置き換えると4つとも 8e-4 で一致し、top-k の選択自体は 0.0% しか変わらない。
MoE だが、ルーティングの判断ではない。

原因は **`capacity_factor: 1.25`**。8B は全 MoE スタックに設定しており、250M は `None`:

```python
capacity = int(counts.max())
if self.cfg.capacity_factor:
    capacity = min(capacity, max(1, math.ceil(N * K / E * factor)))
```

`N` は**その呼び出しの行数**である。学習は数千行を渡して溢れた分を捨て、逐次生成は
1グループずつ渡すので何も捨てない。`capacity_factor = None` を強制するとデコーダ2つは
再び厳密になる（cos 1.000000、修正前は 0.869 と 0.997）。

**この規則に形状非依存版は存在しない。** 「このエキスパートは混んでいたか」はトークン
ではなくバッチについての質問なので、capacity で捨てながら学習したモデルは
バッチ構成の関数であり、どんなキャッシュ管理でも生成が学習を再現できない。
`ScalaForCausalLM` は設定されていると警告するようにした。

**公開モデルへの帰結。** `unofficial-photon-repro-ja-8b-a1b-v2` / `-v3` は、独立した
2つの理由で学習したのとは別の関数から生成しており、後から直せるのは片方だけである。
perplexity は学習時 forward で測るので影響を受けない。250M v1〜v4 は capacity の問題が
なく、ゲート修正後は 98% を示す。

## 8bis. RecGen は自分が生成したものを1ビットも受け取らない

§1〜§8 はすべて**学習**の話だった ── どの目的関数か、content に何を入れるか、
学習と推論のズレをどう埋めるか。以下の測定は学習と一切関係がなく、したがって
**どんな目的関数でも直せない**。

トークンを1つ摂動して、後続トークンのロジットが動くかを見る。未学習の重み、tiny 設定、
`forced_logits` による厳密比較:

| プロトコル | 同じユニット (t34) | **同じメタグループの後のユニット** (t45) | 次のメタグループ (t49) |
|---|---:|---:|---:|
| HierGen | 5.747e-01 | 2.396e-02 | 6.845e-01 |
| ChunkGen | 5.255e-01 | 1.537e-02 | 2.316e-01 |
| **RecGen** | 2.545e-01 | **0.000e+00** | **0.000e+00** |

小さいのではなく**厳密にゼロ**、しかも以降のすべてのグループでゼロである。

導出は2行で済む。RecGen は `X̂` を2つの役割の両方に使う ── level-L デコーダの
content トークンとして、そして上位 chunker への入力として（論文の step (ii)
`Â^(L)_{g+1} := C_θ^(L)(X̂^(L−1)_{I_{g+1}})`）。`X̂_0` は条件付けだけの関数、
`X̂_1` は条件付けと `X̂_0` の関数 ── 帰納的にグループ `g` の `X̂_j` はすべて
`X^(L)_{g-1}` だけの関数である。したがって

```
X^(L)_g = F( C( X̂_{I_g} ) ) = F'( X^(L)_{g-1} )
```

となり、**最上位の軌跡全体がプロンプト末尾の状態からの決定的な展開**になる。
RecGen が出力したトークンは、自分の `C_1` トークンのユニットの外に一切影響しない。
メタグループの `C_L` 個のユニットは同一の文脈から復号される ── 前グループを与えた
条件下で互いに独立である。

**だから4ラウンドどの目的関数も数字を動かせなかった。** `L_rec`、そのレベル制限、
scheduled sampling、`chunk_cond_prob`、式 (6) の文字どおりの解釈 ── すべて
**チャネルが何を運ぶか**を調整するものだった。チャネルに容量がない。7アーム・2サイズで
測った 13〜54% は、「文脈を見ない継続が文脈を見た継続とたまたま一致する率」でしかない。

同時にこれは修理の条件も一意に決める ── **上向きに渡すものを、実際に生成された
トークンに依存させる**しかない。方法は2つしかない: `chunker(生成物)`（線形1つ、
キャッシュ不要）か `encoder(chunker(生成物))`（厳密、キャッシュが要る。§8 の
block-local で安くなる）。

### そこで `mode="recgen"` を修正した

RecGen の本体は**キャッシュ規律**である ── 最上位レベルの KV しか持たない、という
一点であり、14倍の削減はそこから来る。そこは最初から健全だった。壊れていたのは
要約を選ぶ1行だけである。差し替えてもキャッシュ規律も償却も KV の数値も変わらない:

> **§8d 以降の名称について。** 以下の chunker 要約版は現在 `chunkgen` という名前で、

## 8c. 「実装が間違っているのでは」を検証した ── 式 (6) のハット

ここまでの結論に対する当然の反論は「RecGen は論文の手法なのだから、まず自分の実装を
疑うべき」である。これは正しい優先順位であり、実際に**食い違いが1つ見つかった**。

論文の式 (6) はデコーダの content 入力を**ハット付き**で書いている:

```
X̂^(l−1)_{I_g,j} = G_θ^(l)( U^(l)_{g−1} , X̂^(l−1)_{I_g,<j} ; M )
```

ところが `hierarchy.py` の docstring と `architecture.md` §2 はこれを**ハット無し**で
書き写しており、`decode()` は実際に本物のエンコーダ状態を入れていた。文字どおりに
読めば上位デコーダにエンコーダ状態は一切入らず、RecGen の content 代入は代入ですら
なくなる ── 学習時にやっていたことそのものになる。そうであれば `L_rec`,
`self_cond_prob`, `chunk_cond_prob` は**この実装にしかない差**を埋めるための当て物
だったことになる。

論文はどちらとも書いていない（式 (6) は "Generation" の節にあり、目的関数の節は
デコーダが何を消費するかに触れていない）。**なので実装して測った**
（`recursive_decoder_input`）。

### 結果 ── 直る半分と、壊れる別のもの

| arm | token CE | **HierGen** | `xhat_content` | ChunkGen | **RecGen** |
|---|---:|---:|---:|---:|---:|
| ctl | 4.4910 | 98.4% | — | 43.4% | 32.0% |
| fix | 4.5100 | 98.7% | — | 71.1% | 31.0% |
| blocal | 4.5164 | 98.3% | — | 40.8% | 42.7% |
| nolrec | 4.5278 | 97.6% | — | 56.2% | 36.3% |
| **recur** | **5.0477** | **85.5%** | **97.7%** | 54.6% | **50.0%** |

1. **`xhat_content` は 97.7% / KL 0.001。** RecGen の content 代入は狙いどおり
   学習時 forward と一致する。この半分は完全に消えた。
2. **それでも RecGen は 50.0% どまり。** 律速は content 側ではなく `up` 側だった、
   という §7 の切り分けがそのまま確認された。
3. **HierGen が 85.5% に落ちる。** 学習が上位デコーダにエンコーダ状態を一度も
   見せないので、今度は HierGen の方が分布外になる。信頼できる方と安い方が入れ替わる
   だけで、どちらも厳密ではない。

### なぜ CE が 0.53 nats 悪化するのか

`X̂_0` は `U^(l)_{g-1}` だけの関数、`X̂_1` は `U` と `X̂_0` の関数 ── 帰納的に
**グループ `g` 内の `X̂_j` はすべて `X^(L)_{g-1}` だけの関数**である。つまりグループ
`g` の中で実際に生成された内容は、どの条件付けにも到達しない。トークンは**自分の
メタグループ内の、より前のユニットが見えなくなる**（この構成で 12 トークン）。

実測（`test_recursive_input_costs_within_group_context`）: 同じメタグループの前の
ユニットのトークンを摂動すると、teacher forcing では後続トークンのロジットが
2.4e-2 動き、再帰版では **6.0e-7 しか動かない**。次のメタグループはどちらも同じだけ
動く。

これは `architecture.md` §3 が「ちょうど1チャンク幅の盲点」と呼んで避けている失敗
そのものである。よって**式 (6) のハットは生成時の再帰を書いたものであって、学習則
ではない**。teacher forcing こそが §3 の受容野の和をちょうど `t_{<i}` にするもので、
「階層で全文脈を安く配る」ことは PHOTON の主張そのものだからである。

### 副産物 ── Theorem A.6 の前提が精密になった

Definition A.4 は `X̂^(L−1)_{I_g} = X^(L−1)_{I_g}` を要求する。左辺はグループ `g-1`
の関数、右辺はグループ `g` の**中身**の要約である。等号が成り立つには、すべての
メタグループが直前のメタグループから決まっていなければならない ── 16トークン
ブロックの条件付きエントロピーがゼロ、ということである。

**Theorem A.6 は真だが空である。** 前提は未達成なのではなく、予測すべきものが残って
いるモデルには**充足不能**である。これは RecGen についての主張であって PHOTON に
ついてのものではない。アーキテクチャも HierGen も KV 削減も無傷で、§8 の
block-local はその削減を厳密なまま実現する。

## 8d. 修正 ── RecGen の主張はメモリの主張なので、メモリで払う

§1〜§8c は5ラウンドかけて「**どの要約を代入すべきか**」を問うていた。5つとも
負けた。§8bis がその理由を1行で言っている ── 代入する要約はメタコンテキストを
サンプリングする**前**に確定するので、どれを選んでも生成物を運べない。

そこで6ラウンド目は別のことを問う。**そもそも、なぜ代入しているのか。**

RecGen が代入するのは、中間エンコーダの KV キャッシュが `T` に比例して伸びるから
である。それが動機のすべてで、論文自身の要約表もメモリの表である:

| | HierGen | RecGen |
|---|---|---|
| Size | `Σ_l O(T/C_≤l)` | `O(T/C_≤L)` |
| Access | `Σ_l O((T/C_≤l)²)` | `O((T/C_≤L)²)` |

キャッシュの増大を止める方法は、捨てることだけではない。**上限を設ければよく、
その代償は O(1) のメモリであって、代入ではない。** level-`l` エンコーダが
`C_{l+1}` ユニットのブロック `w` 個分だけ遡れるようにすると、保持ユニット数は
永久に一定なので、`T` とともに伸びるキャッシュは最上位だけになる ──
主張は満たされる ── しかも上に渡すのは**本物のエンコーダ状態**なので、代入は
どこにも残らない。`L_rec` も `self_cond_prob` も `chunk_cond_prob` も、補正
すべきものがなくなる。

現在の `recgen` はこのプロトコルである。`enc_window_groups` が `w`。従来の
チャンカ代入版は `chunkgen`、論文どおりの規則は `recgen_paper` に残した。

### 実測 ── 再学習なし

probe モデル（65M dense、2レベル、4×4、5060 Ti 1枚で 30M トークン、`α=0.3`、
`chunk_cond_prob=0`）、系列長 512、すべて教師強制の学習時 forward で採点:

| プロトコル | content / up | 一致率 | **KL** | cos(X_top) | KiB/token |
|---|---|---:|---:|---:|---:|
| `hiergen` | encoder / encoder | 99.2% | 0.0002 | 1.0000 | 0.652 |
| `recgen` w=8 | encoder / encoder | 92.0% | **0.021** | 0.9908 | 0.253 |
| `recgen` w=4 | encoder / encoder | 87.3% | 0.042 | 0.9810 | 0.191 |
| `recgen` w=2 | encoder / encoder | 82.2% | 0.073 | 0.9671 | 0.159 |
| `recgen` w=1 | encoder / encoder | 80.1% | 0.100 | 0.9544 | 0.144 |
| `chunkgen` | chunker / chunker | 70.4% | 0.265 | 0.8378 | 0.128 |
| `recgen_paper` | xhat / xhat | 49.5% | **1.302** | 0.7687 | 0.128 |

**`w=1`（論文の規則より 12.5% 多いメモリ）で KL は 1.302 → 0.100、13分の1に
なる。`w=8`（それでも HierGen の 2.6分の1）では 62分の1。** 窓は連続的な
つまみで、1段上げるごとに O(1) のメモリを払って一致率を買い、極限は HierGen で
ある。

**`cos(X_top)` が `w=1` で 0.77 → 0.95 に跳ねる。** §7 が「誰も学習して
いなかった側」と呼んだ最上位の条件付け状態である。学習されていなかったのでは
なく、**代入できないもの**だった ── 代入をやめれば漂流も止まる。

> **同日中の訂正。** この表の初版は `protocol_diag.load_tokens` が uint32 の
> コーパスを uint16 として読んでいた状態で測っていた。これは例外を出さない ──
> 語彙 99,584 は16ビットに収まらないので、各 id の下位半分と上位半分が交互に

> 壊れた列では `chunkgen` は一致率で勝ち KL で負けており「2つの指標が食い違う」
> と読めたが、本物のトークンでは一致する（70.4% / 0.265 対 49.5% / 1.302）。
> `load_tokens` は manifest.json の dtype を読み、語彙外の id を拒否するように
> した。

### そして Definition A.4 の残差は「学習不足」ではない

`scripts/bottleneck_entropy.py` は、**同じ** `X^(L)_g` から 24 通りのメタ
コンテキストをサンプルし、それぞれが生む本物の `A^(L)_{g+1}` を測る。
`Â^(L)_{g+1}` は抽選前に確定する1点なので、達成しうる上限はその雲の重心である:

```
サンプル間のばらつき     cos = 0.4018   (1.0 なら要約は生成物に依存しない)
どんな Â でも届く上限    cos = 0.6528   (重心)
実測の Â                cos = 0.6130

学習で埋められる分      +0.0399
構造的に届かない分      +0.3472
```

`L_rec` は**埋められるものの 94% をすでに埋めている**。残る 0.35 は16トークン
ブロックの条件付きエントロピーであり、Lemma A.5 はそれをゼロにせよと言っている。
§2〜§6 のどの目的関数も数字を動かせなかったのはこのためで、上限 1.0 ではなく
上限 0.65 に対して最適化していた。

つまり6ラウンドの正直な要約はこうなる ── **論文の Theorem A.6 は正しく、その
前提は「未達成」ではなく「自己矛盾」であり、RecGen の本当の貢献（`O(T/C_≤L)` の
グローバル KV）は、代入ではなく有界キャッシュで買えば無傷で残る。**
`encoder_block_local`（§8）で学習したモデルでは窓が受容野そのものになるので、
`recgen` は学習時 forward とビット一致する
（`test_recgen_is_exact_when_the_window_is_the_trained_receptive_field`）。

**この上限が買い戻せないもの: 計算量。** 中間エンコーダを捨てれば forward も
消えるが、上限を設けるやり方では残る。250M 構成、バッチ32、プロンプト256 +
生成768、3070 Ti 1枚:

| プロトコル | スループット | KV | TPM |
|---|---:|---:|---:|
| `hiergen` | 1008.7 tok/s | 31.1 MiB | 33.2K |
| `recgen` (w=4) | 929.5 tok/s | **8.0 MiB** | **118.3K** |
| `chunkgen` | 1316.4 tok/s | 6.5 MiB | 206.0K |
| `recgen_paper` | 1401.8 tok/s | 6.5 MiB | 219.4K |

`recgen` は HierGen 比で **KV 3.9分の1、TPM 3.6倍、スループット 0.92倍** ──
level-1 エンコーダは依然として走り、読む範囲だけが有界になる。論文の表の
Size 行は完全に達成され、Access 行の一部が「出力が正しいこと」と交換されている。
`recgen_paper` の 1.39倍が、代入に手を伸ばして実際に買えるスループットであり、
一致率 33.1% がその代金である。

## 9. 再現方法

```bash
# プロトコル分解診断（学習時 forward を基準に、代入を分離し、窓幅を掃引）
python scripts/protocol_diag.py --ckpt <ckpt> --data-root data/tokens_ja

# Definition A.4 の残差のうち、学習で埋まる分と構造的に届かない分
python scripts/bottleneck_entropy.py --ckpt <ckpt> --data-root data/tokens_ja

# probe モデル（§8d の表、5060 Ti 1枚で約25分）
python scripts/train.py --config configs/train_probe.yaml

# ブロック局所エンコーダの学習（1アーム約2時間、GB10）
python scripts/train.py --config configs/train_recgen_blocal.yaml
```

### 推奨設定

**既存のチェックポイントで生成するなら、再学習は要らない。** `--mode recgen`
（既定）にして `--enc-window-groups` をメモリ予算に合わせるだけでよい。
`w=1` から始めて、KL が足りなければ上げる。KV が最優先で品質を落としてよい場合
だけ `chunkgen`。`recgen_paper` は論文の規則の再現用で、生成には使わない。

**新規に学習するなら** `encoder_block_local: true` にする。窓が受容野そのものに
なるので `recgen` は厳密になり、目的関数のつまみは全部 0 でよい:

```yaml
rec_loss_alpha: 0.0        # 補正すべき代入が残っていない
chunk_cond_prob: 0.0
levels:
  - encoder_block_local: true    # level-l (l < L) のみ
```

`chunkgen` を主力にする構成（`rec_loss_alpha: 0.30`, `rec_loss_min_level: 2`,
`chunk_cond_prob: 0.25` ── §6 の `fix`）は、KV が 0.128 KiB/token でなければ
ならない場合にのみ意味がある。0.144 まで許せるなら `recgen w=1` の方が
KL で 5 倍良い。
