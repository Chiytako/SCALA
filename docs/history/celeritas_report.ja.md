# CELERITAS 総括レポート

PHOTON（[arXiv:2512.20687](https://arxiv.org/abs/2512.20687)）の非公式再実装から
出発して、3世代ぶんの改訂を設計・実装・測定した記録の総括です。実験の時系列は
[`findings.md`](findings.md)、設計の詳細は [`celeritas.md`](celeritas.md) と
[`fenestra.md`](fenestra.md)、因果性の議論は [`architecture.md`](architecture.md)。
この文書はそれらを独立して読める形に圧縮したものです。

**このプロジェクトの特徴は、主張より撤回のほうが多いことです。** §5 に撤回一覧を
置いてあります。数字はすべて本セッション中のスクリプト出力から貼っています。

## 1. 系譜

| | 何を変えたか | 効いたか |
|---|---|---|
| **PHOTON** | 論文の階層型 LM。4トークン→level-1、4ユニット→level-2（メタ文脈16トークン） | 階層と償却は本物。ただし論文の RecGen は動かない（§2.1） |
| **FENESTRA** | `encoder_window`（中間エンコーダをスライディング窓に）＋ `decoder_lookback` | **−0.112 / −0.158 / −0.111 nats**（2シード幅 0.065） |
| **Celeritas** | `decoder_stream`（デコーダを窓付きストリームに）＋ `pos: nope`（最上位のみ）＋ latent 純化 MLA | **さらに −0.150 / −0.156 / −0.094 nats**。効いたのは stream のみ |
| **Celeritas L=3** | 階層を1段追加（`C_≤L` 16→64） | 品質は同等（+0.0037）、**KV −75%・交差点24倍・局所到達4倍** |

一行ずつの要約:

* **FENESTRA**: 学習時の受容野と生成時のキャッシュ予算を同じ数にする。同じにした
  瞬間、`O(T/C_≤L)` の**厳密**生成がタダになる。
* **Celeritas**: 受容野の再計算をやめる。同じ位置数を盲目なブロックではなく
  1本の窓付きストリームとして流すと、12倍遠くまで届いて計算は44%減る。
* **L=3**: 階層は再帰的なので、段を足せば `O(T²)` の定数が `C²` 分の1になる。

## 2. 各世代が何を直したか

### 2.1 FENESTRA ── 論文の RecGen は代入では成立しない

論文の RecGen は「最上位以外のエンコーダキャッシュを捨て、デコーダ自身の予測
`X̂` を上に渡す」と規定します。**これは構造的に動きません。**

`X̂_j` はスロット `j` が生成される*前*に計算され `X^(L)_{g-1}` だけの関数なので、
`X^(L)_g = F'(X^(L)_{g-1})` ── 最上位の軌跡全体がプロンプトからの決定的な展開に
なります。実測: 生成トークンから後続ユニットへの伝播は**厳密に 0.000e+00**
（未学習の重みでも再現）。

Theorem A.6 は正しく、前提の Definition A.4 が**自己矛盾**しています。
`Â^(L)_{g+1}` はサンプリング前に確定する1点、`A^(L)_{g+1}` は生成物の関数なので、
両者が等しいとは「最上位ストリームが自分の生成物を無視する」ということです。

**直し方**: RecGen が主張しているのは `Σ_l O(T/C_≤l) → O(T/C_≤L)` という
**メモリの主張**なので、キャッシュを*捨てず*に**上限を設ければ**満たせます。
中間エンコーダをスライディング窓で学習し、位相を保ったままロールするキャッシュで
生成する ── これで代入が消え、`recgen` が学習時 forward と**厳密一致**します
（論文規則は同じ重みで KL 2.19）。`L_rec`・`chunk_cond_prob`・`self_cond_prob` は
補正すべき代入が無くなるので全部 0 でよくなります。

### 2.2 Celeritas ── 2つの変更、効いたのは1つ

**`decoder_stream`（効いた）**。`decoder_lookback` は前チャンクを毎グループ・毎層で
**再計算**していました。同じ `R+C` 位置を、盲目なブロックではなく1本の窓付き
ストリームとして連結する ── 位置数は同じ、届く範囲は4トークンから窓幅へ。

| | span/group | L1デコーダ層位置/token | slot 0 の到達 |
|---|---:|---:|---|
| PHOTON (`R=4`) | 8 | 6.000 | なし |
| FENESTRA (`R=1,K=1`) | 9 | 6.750 | 1チャンク=4トークン |
| **Celeritas (`R=1,w=64`)** | **5** | **3.750** | **窓幅（≈51トークン）** |

全体の72%を占めるスタックで **−44%**、しかも12倍遠くまで届きます。

**`pos: nope`（効かなかった）**。2025–26年の hybrid attention は NoPE 全結合層と
RoPE 窓層を**層単位**で交互に積みます（[RNoPE-SWA](https://arxiv.org/html/2501.18795v1)）。
PHOTON はそれを**スタック単位**で既に持っている ── FENESTRA 以降、長さに依存する
スタックは最上位エンコーダ1本だけです。そこに NoPE を置きました。

**結果は品質も長さ頑健性も中立**（held-out −0.1114 vs −0.1115、長さ@16× +0.0254 vs
+0.0262）。「外挿すべき位置テーブルが無い」と「長さ不変」は別物で、NoPE の因果
スタックも学習時の長さ分布から暗黙の位置感覚を学びます。attention sink も効かず。

それでも残す理由は、派生する**削除**が実在するからです:

* MLA の decoupled RoPE key が不要になる（RoPE が weight absorption を通らない
  ためだけに存在していた）→ **`T` で伸びる唯一のキャッシュが −20%**
* weight-absorbed 経路で学習済み sink が使えるようになる
* `rope_theta` / YaRN / 文脈拡張フェーズが選択肢から消え、**`max_seq_len` が
  上限でなくなる**（構造的性質、テストが保証）

### 2.3 L=3 ── 階層は再帰的なので、段を足せば二次の定数が下がる

`configs/celeritas_probe_L3.yaml`。比較を有利にではなく**曖昧でなく**するため、
**level 1 は完全同一**、中間レベルは旧トップから切り出して自弁、**層位置/token は
両方ちょうど 5.875**。パラメータ +0.44%。

**コードは1行も変えていません。** `_emit_group` は再帰、キャッシュ確保も prefill も
レベルをループ、会計はレベル単位 ── 初回実行で `recgen` が 4.8e-06 で一致。

## 3. 測定結果

### 3.1 品質（未学習領域3スライス、日英2言語、各262Kトークン）

各スライスの2シード平均に対する差分:

| アーム | ja@48M | ja@60M | en@40M |
|---|---:|---:|---:|
| PHOTON (seed A / B) | +0.0323 / −0.0323 | +0.0345 / −0.0345 | +0.0021 / −0.0021 |
| FENESTRA full | −0.1115 | −0.1579 | −0.1112 |
| Celeritas: NoPE のみ | −0.1114 | −0.1590 | −0.1083 |
| Celeritas: stream のみ | −0.2618 | −0.3121 | −0.2022 |
| **Celeritas** | **−0.2615** | **−0.3146** | **−0.2065** |
| 2シード幅 | 0.0645 | 0.0689 | 0.0042 |

2×2 は**完全に加法的**（交互作用なし）で、帰属は曖昧さがありません。

### 3.2 長さ外挿（同一トークンを採点、前に置く文脈量だけ変える。正=劣化）

| 文脈 | ×学習長 | PHOTON | FENESTRA | NoPEのみ | streamのみ | **Celeritas** |
|---|---:|---:|---:|---:|---:|---:|
| 8192 | 16× | **+0.4019** | +0.0262 | +0.0254 | −0.0000 | **−0.0001** |

PHOTON の 0.40 のうち **0.376 は level-1 エンコーダが大域 RoPE** だったこと。
FENESTRA が `encoder_window` でそこを窓に閉じた時点で消えていました ──
**有界スパンはメモリ機構であると同時に長さ汎化機構**です（副産物）。

残りを消しているのは NoPE ではなく `decoder_stream` の方でした。ただし
**平坦さの正体は頑健性ではなく無関心**です（下記）。

### 3.3 `decoder_stream` 窓幅スイープ（学習計算量は幅に依らず完全一致）

| `w` | トークン | ja@48M | 長さ@16× | KL(512 vs 8192) | ctx 256–512 |
|---:|---:|---:|---:|---:|---:|
| block | 4 | −0.1115 | +0.0262 | 0.01736 | +0.0019 |
| 8 | 6 | −0.0792 | +0.0223 | 0.01809 | +0.0032 |
| 16 | 12 | −0.1076 | +0.0110 | 0.01085 | +0.0043 |
| 32 | 25 | −0.1659 | +0.0016 | 0.00294 | +0.0017 |
| **64** | 51 | **−0.2615** | **0.0000** | 0.00004 | −0.0001 |
| 128 | 102 | −0.3017 | 0.0000 | 0.00006 | +0.0013 |
| 256 | 204 | −0.3382 | 0.0000 | 0.00006 | +0.0021 |

* **長さ曲線は窓幅の単調関数で、`w=64` でゼロに飽和。**
* **KL がそれに1段ずつ連動** ── 平坦さは「参照するのをやめた」ことの表れ。
* **品質は飽和しない**（w=256 でも改善が続く）。
* **どの窓幅でも 256–512 帯は ≤0.0043 nats** ── 窓を狭めても仕事は階層に戻らない。

個々の段差の多くは2シード幅の内側ですが、**7アームの単調順序が2スライス＋train CE の
3統計量で再現する**ことが証拠です。

### 3.4 検索プローブ（`copy_diag.py`）── 本セッションで最も重要な計測

16トークンのスパンを距離 `d` で反復し、**2回目だけを採点**。対照は同位置の
無関係な実スパン。差が「距離 `d` での検索の価値」です。

**対照の境界は level-1 デコーダ窓ではありません。** 非大域の到達距離は
「スパンが有界な全スタックの最大値」で、いちばん深いものが効きます:

| arm | `C_≤L` | 非大域の到達距離 |
|---|---:|---:|
| PHOTON | 16 | 16 tokens |
| FENESTRA | 16 | 64 |
| **Celeritas** | 16 | **171** |
| **Celeritas L=3** | 64 | **682** |

**結果1 ── 階層は検索している**（`seq_len` 1024、`d ∈ {192,…,768}` の平均）:

| arm | 平均 copy gain | d=768 |
|---|---:|---:|
| PHOTON | **+0.897** | +0.793 |
| FENESTRA | **+0.827** | +0.720 |
| Celeritas | **+0.868** | +0.790 |

`seq_len 4096` まで広げると、**学習文脈 512 の6倍の距離**でも +0.99〜1.81 nats。

**結果2 ── 固定グリッドの代償は約0**（aligned vs offset、6アーム）:
**−0.0000 〜 +0.0004 nats**（最悪ペア 0.0018）。効果量 0.85 に対して桁が3つ違います。

**結果3 ── 粒度の壁も8倍振って動かない**:

| `C_≤L` | 1ベクトルあたり | copy gain 平均 |
|---:|---:|---:|
| 8 | 8 tokens | +1.2948 |
| 16 | 16 tokens | +1.2990 |
| 64 | 64 tokens | +1.2906 |

振れ幅 0.0084 nats、しかも単調ですらありません。

### 3.5 L=3 のコストと効能

| | L=2 | L=3 |
|---|---:|---:|
| held-out CE @2048 | 4.8128 | 4.8165 (**+0.0037**) |
| 64トークン以遠の文脈利用 | +0.0640 | +0.0632 |
| copy gain (d=768–1536) | +1.2990 | +1.2906 |
| **attention が他を追い越す文脈長** | 1.75M | **41.5M トークン** |
| **KV/token @ 32K（厳密 `recgen`）** | 0.1003 KiB | **0.0249 KiB** |
| 非大域の到達距離 | 170 | **682 tokens** |
| 層位置/token | 5.875 | 5.875 |

> **誰も設計していなかった副産物**: いちばん深いデコーダの窓は*粗いユニット*単位
> なので、**階層1段で局所（厳密キャッシュ・O(1)/token）の到達距離が `C` 倍**に
> なります。逆に、深い階層は大域ストリームをより不要にもします
> （KL(2048 vs 8192) は L=2 で 0.00052、L=3 で **0.00000**）。

### 3.6 生成コスト

| | PHOTON | FENESTRA | Celeritas |
|---|---:|---:|---:|
| 層位置/token | 8.375 | 8.875 | **5.875** |
| stacks FLOP/token | 26.5 M | 28.1 M | **18.6 M** |
| 合計 FLOP/token | 103.2 M | 104.7 M | **95.6 M** |
| 学習ピークメモリ | — | 5.45 GiB | **4.91 GiB** |
| 生成 tok/s（batch 8, 短文脈） | 553 | 538 | 500 |

**実測スループットは FLOP 差を見ません**（65M・batch 16 では launch-bound）。
毎回再現したのは**活性メモリ −9.9%** です。生成は短文脈で約4%遅くなります
（毎トークン 9 位置ではなく 64 位置を採点するため。`T` には依存しません）。

**投機デコード**（`mtp_depth: 3`、8プロンプト、batch 1、greedy）:

| | 平均 | 最良 | 最悪 |
|---|---:|---:|---:|
| 速度比 | **1.15×** | 1.39× | 0.99× |
| 採択率 | 48.4% | 98.4% | 0.0% |
| L1呼び出し/chunk | — | 2.09 | 4.08（逐次=4） |

**全プロンプトで出力がトークン単位で完全一致。** batch 4 以上では効きません
（1本の共有キャッシュは行ごとに違う量だけ進めないため）── レイテンシの最適化です。

## 4. 計測器と、それが支えられる範囲

| 計測器 | 何を測るか | 支えられないこと |
|---|---|---|
| `protocol_diag.py` | 生成プロトコル間の一致率・KL | 一致率は bf16 のタイブレーク指標。KL が本命 |
| `context_diag.py` | 遠方文脈を雑音で潰したときの損失 | **普通のテキストの平均**。能力ではなく需要を測る |
| `position_diag.py` | メタ文脈内の位置別 CE | 相対値のみ |
| `length_diag.py` | 学習長より先での CE 劣化 | 「平坦＝頑健」とは言えない（下記） |
| `length_sensitivity.py` | 文脈長を変えたときの**分布**の変化 | **「頑健」と「無関心」を分ける唯一の計測器** |
| `copy_diag.py` | 距離 `d` での検索の価値、グリッド整列の影響 | 語彙・スパン長・スケールに依存 |
| `window_sweep.py` | 上記を窓幅で束ねる | — |
| `arm_table.py` | 2シード平均に対する差分表 | 2シード幅は信頼区間ではない |
| `accounting.py` | パラメータ・FLOP・KV の解析値 | `layer_positions_per_token` は**計算量ではない** |

**このプロジェクトで繰り返し起きた失敗は「指標を支えられる範囲の一段外で使う」
ことです。** 4回起きました（§5）。

## 5. 撤回した主張の一覧

| 撤回したもの | なぜ間違っていたか |
|---|---|
| 「計算 −39%・KV −40% で CE 変化なし」 | `layer_positions_per_token` は LM head を0円で数えていた（`d=384` では head が74%）。実測スループットは **−5%** |
| 診断スクリプトの CE 全般（2026-07-30 以前） | uint32 コーパスを uint16 で読んでいた。例外は出ず、CE 12.49 vs 学習時 4.80 |
| 一致率全般（2026-07-29 以前） | weight-absorbed MLA が attention 出力ゲートを落としていた（`w_gate` 初期値0なので未学習では観測不能） |
| 「seed floor 0.053 nats」 | `--tail` の関数だった。k∈{3,5,8,10,15} で 0.0046〜0.0535、順位も反転 |
| 「NoPE が長さ外挿を直す」 | ablation で **+0.0254 vs +0.0262**。直しているのは `decoder_stream` |
| 「窓幅は長距離チャネルを取り戻すノブ」 | スイープで否定。どの幅でも 256–512 帯は ≤0.0043 |
| **「どのアームも役に立つ長距離チャネルを持っていない」** | **コーパスの性質をモデルの能力と取り違えていた。** 検索可能なものを置けば +0.85 nats 出る |
| `copy_diag` の整列 assertion（自作） | 整列条件は「p1 が境界にある」ではなく「p1 ≡ p2 (mod C)」。正しいスイープを誤って拒否した |
| `copy_diag` のペア判定（自作） | aligned/offset で境界判定が非対称になり、FENESTRA に架空の −0.05 グリッド代償を作った |

## 6. Transformer / Mamba との位置づけ

| | 生成時の状態 | 注意の総計算 | 遠方の取り出し | 学習の並列化 | 専用カーネル |
|---|---|---|---|---|---|
| **Transformer** | `O(T)` | `O(T²)` | **厳密・全位置** | 完全 | 成熟 |
| **Mamba / SSM** | **`O(1)`** | **`O(T)`** | 有損失（固定状態に圧縮） | scan | **必須** |
| **Celeritas L=2** | `O(T/16)` | `O(T²/256)` | 厳密（16トークン粒度） | 完全 | **不要** |
| **Celeritas L=3** | `O(T/64)` | `O(T²/4096)` | 厳密（64トークン粒度） | 完全 | **不要** |

**Mamba は時間を固定状態に畳み込む（忘れる）。PHOTON は解像度を落として時間を全部
保持する（ぼかす）。** 失敗モードが違います ── そして本セッションの測定では、
**その「ぼかし」は算術が示唆するほど損失的ではありませんでした**（粒度8倍で
0.008 nats）。

漸近クラスは Transformer と同じ二次で、定数が `C_≤L²` 分の1。L=3 で交差点は
41.5M トークン（同じ幅の dense Transformer なら約1万トークン）。**Mamba の線形とは
別物**です。

## 7. 現状 ── 検証済みと未検証

### 構造的に検証済み（任意の重みで成立、テスト62件）

* 生成（`hiergen` / `recgen`）が学習時 forward と厳密一致。実重みで **KL ~1e-9・
  argmax 一致 100%**
* 因果性: 全128位置を摂動して後方影響 **厳密に 0.000e+00**
* キャッシュは `T` に依らず有界（最上位を除く）
* **位置範囲を出るスタックが存在しない** → 最大文脈長という概念が無い
* 任意の系列長を受け付け、整列版と厳密一致
* 投機デコードが逐次デコードと**トークン単位で完全一致**
* 3階層が無改修で動作し、局所到達距離が `C` 倍になる

### 測定済み（n=1・65M・30Mトークン）

* `decoder_stream` の品質改善（2シード幅の2.3倍、3スライス2言語で同符号）
* 長さ曲線が窓幅の単調関数であること
* 階層が距離192〜3072トークンで +0.85〜1.8 nats の検索を提供すること
* 固定グリッドと粒度の代償が測定限界以下であること
* L=3 が品質を落とさずに KV を1/4にすること

### 未検証

* **250M 以上での再現**（`celeritas_small.yaml` / `celeritas_small_L3.yaml` は未学習）
* 8シードの分散分解（2シード幅は信頼区間を持たない）
* **遠方チャネルが「役に立つ」条件**。普通の Wikipedia は 256トークン以遠を
  ≤0.005 nats しか使いません。長文書・コード・多ターン対話なら違うかもしれませんが、
  ここには証拠がありません
* 温度サンプリング下での投機デコード（`min(1, p/q)` 規則が未実装）
* 長文脈での**学習**（すべて 512 または 2048 で学習し、それより先を推論で試している）

## 8. 次に何をすべきか

測定が指している方向は、アーキテクチャではなく**データ**です。

1. **遠方チャネルが仕事をするコーパスを見つける**。これが最優先で、
   アーキテクチャ作業では答えが出ません。`copy_diag.py` は能力があることを
   示しました。需要がある領域（長文書・コード・対話）で `context_diag` を
   走らせるのが次の一歩です。
2. **250M で再現する**。probe の結論はすべて n=1・65M です。
3. **バイト単位版で `copy_diag` を再走**。固定グリッドと粒度の帰無結果は
   99,584語彙のサブワードという条件の性質かもしれません。1チャンクが数文字に
   なる条件では違う答えが出る可能性があります。
4. 動的チャンキング（H-Net）は**この規模では作るべきではありません**（§3.4 結果2）。

## 付録: 主要な設定

```yaml
# Celeritas の中核
levels:
  - chunk_size: 4
    converter_width: 1
    encoder_window: 16        # 中間エンコーダはスライディング窓 → recgen が厳密
    decoder_stream: 64        # デコーダは窓付きストリーム → 層位置 −44%
    encoder: {attention: {kind: gqa, pos: rope}}     # スパン有界 → RoPE は厳密
    decoder: {attention: {kind: gqa, pos: rope}}
  - chunk_size: 4
    converter_width: 2
    decoder_stream: 64
    encoder:                  # 唯一 T で伸びるスタック
      attention:
        kind: mla
        pos: nope             # 最大文脈長という概念が消える
        mla_qk_rope_head_dim: 0   # decoupled key 削除 → 唯一伸びるキャッシュ −20%
        attn_sink: true
        qk_norm: false        # weight absorption に必要
rec_loss_alpha: 0.0           # 代入が無いので補正も要らない
chunk_cond_prob: 0.0
```
